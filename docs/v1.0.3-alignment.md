# MVP v1.0.3 alignment audit and verification

## Scope and result

This is a **partial implementation alignment**, not a completed backend. The
checkout began as a skeleton: Express starts without routes, Prisma has only a
generator/datasource, the worker has no registered jobs, and domain directories
contain `.gitkeep`. There were no existing tests, provider adapters, authentication
handlers, database models or financial effects to correct. Building all of these
would be a greenfield implementation rather than a targeted repair.

### Already correct and preserved

- Modular monorepo boundaries, Express/Prisma/PostgreSQL, BullMQ/Redis tooling.
- OpenAPI as canonical source, `openapi-typescript` and the read-only drift checker.
- SupplierProduct master inventory and retailer listing references; inventory
  total/reserved/available counters and version, fulfillment allocation quantities.
- Separate orders/items/fulfillments/shipments; business membership and ownership
  authorization requirements; standard error envelope and NGN minor-unit money.
- Existing valid domain endpoints, single-store carts and checkout, analytics,
  notifications, aggregation and bulk requests. No new endpoints were added.
- Existing CI jobs/services and deployment workflow. No brand rename.

### Conflicts found and corrected

- Old order/payment/fulfillment/shipment enums; absent escrow and settlement states.
- No explicit final financial gate or multi-supplier settlement read model.
- Entrepreneur business type and obsolete in-hub holding field/state/documentation.
- Missing payment-method restriction and arbitrary status query filters.
- Generic webhook signature/native payload mismatch.
- No product grouping field on demand batches.
- Main CI (which gates deployment) did not itself validate the contract or type drift.

## Contract changes

`info.version` is now `1.0.3`. This is an explicitly documented **pre-release
breaking correction**: `/v1` is retained because this checkout has no implemented
routes. It does not claim compatibility with any externally deployed consumers.
Removed enum members/holdingUntil and new required request/model fields would
require consumer coordination if such consumers exist elsewhere.

- Exact `OrderState`, `PaymentState`, `EscrowState`, `FulfillmentState`,
  `ShipmentState`, `SettlementState` enums. Existing `*Status` schema names are
  aliases, preserving references without maintaining duplicate enum definitions.
- Separate read-only order escrow/settlement collections, with payment, order,
  fulfillment, supplier and shipment relationships. One settlement/escrow portion
  per supplier fulfillment; portions must reconcile to actual held funds.
- All-settled completion, all-delivered eligibility, trusted reconciliation and
  pre-fulfillment cancellation rules explicitly documented.
- BANK_TRANSFER/USSD payment initialization; adapter-based native signed webhook
  contract, durable duplicate acknowledgement and conflict responses. The
  normalized event schema is explicitly internal, not the provider wire body.
- Shared atomic reservation requirements and stock conflict semantics; no new
  independent stock pool or retailer-owned physical inventory.
- Product-keyed aggregation and individually labeled cross-dock packages; failed
  shipment returns to supplier, not in-hub holding.
- Domain conflict codes use the existing ErrorResponse envelope.
- Customer remains an identity, not a business type. Enterprise extends Supplier.
  Discovery remains directory-only and checkout remains single-store.

## Backend guard coverage

`apps/api/src/modules/orders/lifecycle.ts` uses generated OpenAPI types. It contains
pure guards for payment, fulfillment and shipment progression, settlement
eligibility, trusted settled reconciliation and final order completion. Completion
requires confirmed payment, a non-empty complete fulfillment plan, exactly one
settlement per planned fulfillment, delivered shipment coverage, settled records
and correctly associated released escrow. Empty, duplicate, missing or mismatched
relationships cannot satisfy the completion guard.

These functions are **not wired into HTTP routes, transactions or workers**. The
caller must load the full authoritative aggregate in a transaction; passing a
client-supplied or filtered plan cannot establish correctness. The functions do
not authenticate a webhook, reserve stock, send money or persist anything.
Repeated reconciliation yields the same state; that is not proof of exactly-once
external financial effects.

### Tests

19 unit tests cover requested scenarios 1–9 at the guard level, repeated guard
execution (part of scenario 10), exact generated enum unions checked by TypeScript,
terminal/invalid transitions, missing associations, multi-shipment eligibility,
and multi-supplier completion. Existing tests were not removed (none existed).

**Not covered:** actual webhook/job replay with durable financial deduplication
(scenario 10), two simultaneous transactions reserving the last stock unit
(scenario 11), or Business A making an HTTP request for Business B's resource
(scenario 12). There are no handlers, persistence layer or authorization layer
against which to run those tests. No mock test is presented as database or HTTP
integration proof.

## Remaining implementation work / release blockers

1. Prisma domain models and initial migrations, including scoped relationships,
   payment/provider reference uniqueness, complete fulfillment plans and financial
   reconciliation constraints. No migration was created: there is no existing
   database domain schema to migrate or preserve.
2. Actual provider adapters verifying raw bytes, amount/currency/reference,
   durable webhook inbox/deduplication and payment conflict reconciliation.
3. Atomic all-line stock reservation using conditional updates/row locks and
   rollback on insufficient inventory; durable allocation and release records.
4. Settlement/provider reconciliation, escrow release/refund orchestration,
   transactional outbox and idempotent workers/notifications. A pure guard does
   not make a cross-service money transfer atomic.
5. Authentication and server-side business/store/customer ownership predicates
   for every read/write. Never use client business IDs or frontend filtering as
   authorization. Supplier views must not leak other suppliers' financial data.
6. HTTP request validation, standardized error mapping, permission-checked
   operational transitions, concurrency-safe cancellation and aggregation jobs.
7. Real PostgreSQL/Redis/provider-adapter integration tests for scenarios 10–12.
8. Previously documented guest checkout/cart ownership design gaps and other
   unsuperseded findings in `contract-review.md` remain unresolved.

## CI/CD changes

- Main `ci.yml` quality job now runs `validate:api` and `check:api-types`, ensuring
  the existing deployment's successful-CI requirement includes contract checks.
- Dedicated `api-contract.yml` reuses those scripts instead of overwriting the
  committed types, and watches changes to the checker itself.
- Installation, format, lint, typecheck, tests, build, integration services and
  deployment structure remain unchanged. CI never commits generated files.
