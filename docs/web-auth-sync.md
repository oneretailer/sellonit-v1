# Web auth sync with the live API

> **Update (auth routing rework):** the post-onboarding routing described below
> (item 9 and the `roleApi.getRecommendation` table) has been replaced by a
> single server-data-driven destination function and the retailer/entrepreneur
> custom 404. See `docs/auth-redirect-rework.md`.

Date: 2026-10-30 · Scope: `apps/web` only (no changes to `apps/api`, `apps/worker`,
`packages/*`, the OpenAPI spec or the generated types).

The backend is the source of truth. The contract below was read from
`apps/api/src/http/routes/auth.routes.ts`, `apps/api/src/modules/auth/auth.handlers.ts`,
`apps/api/src/modules/auth/auth.service.ts`, `docs/openapi.yaml`,
`packages/shared/src/api.d.ts`, `docs/auth-registration-contract.md` and
`docs/v1.0.3-alignment.md`. Every route is mounted under `/api/v1`; the web app
calls the same-origin `/api/v1/*` proxy. All errors use
`{ "error": { "code", "message", "requestId" } }` — there is no `fields` key.

Not implemented by the backend (the frontend keeps a graceful, network-free state):

- `POST /auth/resend-verification` — specified in `docs/auth-registration-contract.md` §4.
- `POST /auth/refresh`, `POST /auth/logout` — listed in `docs/openapi.yaml`, not mounted in `auth.routes.ts`.
- No code-based or OTP-based **account** verification and no phone login: every auth field is validated as an email address.

## 3. Backend gaps and ambiguities

1. **Email verification resend** (`POST /auth/resend-verification`) is specified but missing; the UI explains that it is unavailable and makes no request.
2. **No code/OTP account verification.** The `/auth/verify-account` screen can only be reached through the login "unverified" branch; it now explains that verification is link-based. `verifyCode` refuses to call a route that would always answer `INVALID_CODE`.
3. **`POST /auth/verify-email` does not create a session** although `docs/auth-registration-contract.md` §3 requires it. The web app therefore uses `/auth/verify-email-and-login` (instant login) and this is the only verification call it makes.
4. **No reset token.** `/auth/verification-codes/verify` only proves the code; `/auth/reset-password` re-checks it. The contract's "short-lived reset token" is not implemented, so the verified code is held in memory for the next step.
5. **Phone identifiers / phone login are not supported** (login, forgot password and reset all validate `email`). The screens keep the "Email or phone number" field but a phone now fails locally with an explicit message instead of a misleading server error. A backend `identifier` + `identifierType` contract would be needed to finish the design.
6. **`fullName` vs `firstName`/`lastName` and `422` + `fields`**: the contract wants `fullName`, `422` with per-field messages; the backend wants `firstName`/`lastName` and answers `400` without `fields`. The client sends both naming styles and maps `409`/`429`/`fields` when present.
7. **`/auth/me` is not documented in `docs/openapi.yaml`** (only `/me` is), while `/auth/refresh` and `/auth/logout` are documented but not mounted. The generated types therefore overstate what exists.
8. **Role → business type mapping**: the UI role `supplier` has no `BusinessType` member; it is stored as `ENTERPRISE` ("Enterprise extends Supplier", `docs/v1.0.3-alignment.md`). Product should confirm.
9. **Post-onboarding routes are still local.** The backend stores the intent but exposes no role-specific dashboard routing, so `roleApi.getRecommendation` keeps deciding the destination.
10. **`AUTH_AUDIT.md` is stale** on the topics above (it predates the forgot/reset/onboarding endpoints) and was left untouched; this document supersedes its auth-endpoint inventory.
